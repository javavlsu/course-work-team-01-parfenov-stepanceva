# Нагрузочное тестирование Kanban API с помощью Apache JMeter

Документ описывает методику, сценарии и результаты нагрузочного тестирования
REST API серверной части проекта (Spring Boot, модуль `src/Backend`).

- **Дата проведения:** 17.05.2026
- **Инструмент:** Apache JMeter 5.6.3
- **Тестируемое приложение:** `kanban-0.0.1.jar` (Spring Boot 4.0.2, Java 21)
- **Файл плана тестирования:** [kanban-test-plan.jmx](kanban-test-plan.jmx)
- **Скрипт запуска:** [run-tests.ps1](run-tests.ps1)

---

## 1. Объект тестирования

Тестируется REST API канбан-доски. Базовый контекст приложения — `/kanban/api`.
В нагрузку включены следующие эндпоинты:

| № | Метод и путь | Назначение | Тип |
|---|--------------|------------|-----|
| 01 | `POST /kanban/api/auth/registration` | Регистрация нового пользователя | Подготовка |
| 02 | `POST /kanban/api/auth/login` | Вход в систему | Подготовка |
| 03 | `POST /kanban/api/groupteams/` | Создание группы (нужна для создания досок) | Подготовка |
| 10 | `GET /kanban/api/boards/` | Получение списка досок пользователя | Основной тест |
| 11 | `POST /kanban/api/boards/` | Создание новой доски | Основной тест |
| 12 | `GET /kanban/api/groupteams/` | Получение списка групп пользователя | Основной тест |
| 13 | `GET /kanban/api/users/profile` | Получение профиля пользователя | Основной тест |

### Особенности аутентификации

Приложение использует **JWT-токены, передаваемые через cookie** (`accessTokenKanban`,
`refreshTokenKanban`). Cookie помечены как `HttpOnly` и `SameSite=Strict`.

В тестовом плане за это отвечает элемент **HTTP Cookie Manager**: после регистрации
или входа JMeter автоматически сохраняет полученные `Set-Cookie` и подставляет их
во все последующие запросы того же потока. Опция «очищать cookie между итерациями»
отключена (`clearEachIteration=false`), поэтому поток остаётся авторизованным на
протяжении всего теста.

## 2. Архитектура тестового плана

Тестовый план — единый файл `kanban-test-plan.jmx`, параметризованный через
свойства командной строки (`-Jthreads`, `-Jrampup`, `-Jloops`, `-JrunId`).
Это позволяет одним планом проводить все сценарии, меняя только параметры запуска.

```
Test Plan
├── HTTP Request Defaults        — host/port, таймауты (connect 10с, response 30с)
├── HTTP Cookie Manager          — хранит JWT-cookie между запросами потока
├── HTTP Header Manager          — Content-Type / Accept: application/json
└── Thread Group (Пользователи Kanban)
    │   threads = ${__P(threads)}, ramp-up = ${__P(rampup)}, loops = ${__P(loops)}
    │
    ├── [ЭТАП ПОДГОТОВКИ]  Once Only Controller — выполняется 1 раз на поток
    │     ├── 01 POST Регистрация            → assert 201
    │     ├── 02 POST Вход                   → assert 200
    │     └── 03 POST Создание группы        → assert 201, извлечение groupId (JSON Extractor)
    │
    └── [ОСНОВНОЙ ТЕСТ]  тело цикла — повторяется loops раз на поток
          ├── 10 GET Список досок            → assert 200
          ├── 11 POST Создание доски         → assert 201 (использует извлечённый groupId)
          ├── 12 GET Список групп            → assert 200
          └── 13 GET Профиль пользователя    → assert 200
```

### Стадия подготовки (обязательное условие)

Этап подготовки помещён в **Once Only Controller** — он выполняется **ровно один раз
для каждого виртуального пользователя (потока)** перед входом в основной цикл:

1. **Регистрация** — создаётся уникальный пользователь. Уникальность достигается
   за счёт подстановки `${__threadNum}` (номер потока) и `${__P(runId)}`
   (идентификатор запуска): email вида `jm<номер_потока>x<runId>@jmeter.test`.
   Это исключает конфликт `409 Conflict` («email уже занят») как внутри одного
   прогона, так и между повторными запусками.
2. **Вход** — выполняется логин тем же пользователем; обновляются JWT-cookie.
3. **Создание группы** — личные доски в приложении нельзя создать без группы
   (сервер возвращает `403 «Not a group member»`). Поэтому на этапе подготовки
   создаётся группа, а её `id` извлекается из JSON-ответа (`JSON Extractor`,
   путь `$.id`) в переменную `groupId`.

Только после успешного прохождения всех трёх шагов поток переходит к основному
тесту. Извлечённый `groupId` используется при создании досок (запрос 11).

### Контроль корректности

К каждому запросу прикреплён **Response Assertion**, проверяющий код ответа
(201 для создания, 200 для чтения). Любой неверный код помечает выборку как
ошибочную и попадает в столбец `Error %` итогового отчёта.

## 3. Сценарии тестирования

| Сценарий | Потоки | Ramp-up | Циклов | Всего запросов | Цель |
|----------|:------:|:-------:|:------:|:--------------:|------|
| **smoke** (дымовой) | 1 | 1 с | 5 | 23 | Проверка работоспособности плана и API |
| **load** (нагрузочный) | 20 | 20 с | 10 | 860 | Поведение под умеренной постоянной нагрузкой |
| **multithread** (многопоточный) | 50 | 1 с | 5 | 1150 | Конкурентный доступ — все потоки стартуют почти одновременно |
| **stress** (стресс) | 100 | 10 с | 10 | 4300 | Поведение под повышенной нагрузкой |

Расчёт количества запросов: `потоки × (3 запроса подготовки + циклы × 4 запроса)`.

**Пояснение к параметрам:**
- *Потоки (threads)* — число виртуальных пользователей.
- *Ramp-up* — время, за которое запускаются все потоки. Малый ramp-up при большом
  числе потоков (сценарий `multithread`) создаёт пиковую конкурентную нагрузку.
- *Циклов (loops)* — сколько раз каждый поток повторяет блок основного теста.

## 4. Как запустить тесты

### Предварительные требования

1. **MySQL** запущен на `localhost:3306`, база `Kanban` доступна
   (профиль `local`, см. `src/main/resources/application-local.yml`).
2. **Бэкенд** собран и запущен:
   ```powershell
   $env:JAVA_HOME = "C:\Program Files\Java\jdk-25"
   cd src\Backend
   .\mvnw -DskipTests clean package
   java -jar target\kanban-0.0.1.jar
   ```
   Приложение должно отвечать на `http://localhost:8080/kanban/api`.
3. **Apache JMeter 5.6.3** установлен (по умолчанию `C:\Program Files\apache-jmeter-5.6.3`).

### Запуск всех сценариев

```powershell
cd src\Backend\jmeter
.\run-tests.ps1
```

### Запуск одного сценария

```powershell
.\run-tests.ps1 -Scenario load
```

### Запуск вручную через JMeter

```powershell
$env:JAVA_HOME = "C:\Program Files\Java\jdk-25"
& "C:\Program Files\apache-jmeter-5.6.3\bin\jmeter.bat" -n `
    -t kanban-test-plan.jmx `
    -l results\load.jtl -e -o results\load-report `
    -Jthreads=20 -Jrampup=20 -Jloops=10 -JrunId=manual01
```

После выполнения по каждому сценарию формируется HTML-дашборд:
`results\<сценарий>-report\index.html`.

> **Замечание по окружению.** JMeter 5.6.3 поставляется с устаревшей версией
> Groovy, несовместимой с байт-кодом JDK 25 (`Unsupported class file major version 69`).
> Поэтому в тестовом плане **намеренно не используются JSR223-скрипты** — генерация
> уникальных данных выполнена встроенными функциями JMeter (`__threadNum`, `__P`,
> `__counter`). План полностью работоспособен на JDK 25.

## 7. Анализ и выводы

1. **Стабильность.** Во всех четырёх сценариях (суммарно 6333 запроса) — **0 ошибок**.
   Приложение корректно обрабатывает как одиночные запросы, так и конкурентную
   нагрузку до 100 пользователей.

2. **Чтение vs запись.** GET-эндпоинты (`/boards`, `/groupteams`, `/users/profile`)
   стабильно отвечают за единицы миллисекунд. Это самые «дешёвые» операции.

3. **Регистрация и вход — самые медленные операции.** Регистрация — 120–200 мс,
   вход — 57–190 мс. Причина — хеширование пароля алгоритмом **BCrypt**
   (`BCryptPasswordEncoder` в `SecurityConfig`). BCrypt намеренно ресурсоёмкий,
   и такое поведение нормально — оно не является дефектом, а защищает от подбора
   паролей. Именно поэтому регистрация/вход вынесены в **однократный этап
   подготовки**, а не повторяются в цикле.

4. **Влияние конкуренции.** Сравнение `multithread` (ramp-up 1 с) и `stress`
   (ramp-up 10 с) показывает: решающий фактор деградации — не общее число
   пользователей, а **скорость их одновременного подключения**. При резком
   старте 50 потоков среднее время отклика выросло до 90 мс, при плавном
   разгоне 100 потоков осталось на уровне 15 мс. Отказов не было ни в одном случае.

5. **Пропускная способность** при многопоточной нагрузке — порядка
   **400+ запросов/с** на локальной машине, что является хорошим показателем
   для учебного проекта.

### Рекомендации

- Тестирование проводилось на локальной машине (приложение, БД и JMeter вместе),
  поэтому абсолютные числа отражают в том числе нагрузку на ОС. Для объективной
  оценки желательно запускать JMeter с отдельного хоста.
- Для проверки пределов системы можно увеличить нагрузку (например, 200–500
  потоков) и/или включить планировщик длительности (`Scheduler`) в Thread Group.
- Имеет смысл добавить сценарий с обновлением и удалением сущностей
  (`PUT/DELETE /boards`, `/groupteams`) для более полного покрытия API.
- Тест создаёт реальные записи в БД. После прогонов рекомендуется очищать
  тестовые данные (пользователи `jm*@jmeter.test`, группы `JMGroup *`).

## 8. Структура каталога `jmeter/`

```
jmeter/
├── kanban-test-plan.jmx                  — параметризованный план тестирования JMeter
├── run-tests.ps1                         — скрипт запуска всех сценариев
├── JMeter-нагрузочное-тестирование.md     — данный документ
└── results/
    ├── smoke.jtl        + smoke-report/        (HTML-дашборд)
    ├── load.jtl         + load-report/
    ├── multithread.jtl  + multithread-report/
    └── stress.jtl       + stress-report/
```

Для просмотра подробного отчёта откройте `results/<сценарий>-report/index.html`
в браузере — там доступны графики времени отклика, пропускной способности,
перцентилей и распределения по запросам.
